# 閾値の校正根拠

CLAUDE.md に書かれた「この閾値を緩めるな」の**根拠となる実測値**を置く。CLAUDE.md 側には規則だけを残し、数値はここに集約する。

**この文書の値はすべて「幻想交響曲 第4楽章（幻想4）」の特定の built dir / 入力 wav に対する実測値**であり、他曲の絶対基準ではない。曲を変えたら各項の「再校正手順」に従って測り直すこと。

参照録音: ベルリン・フィル録音（281.04s / 178 measures）。別演奏 = 同じ楽章の別オーケストラ録音。

---

## 1. mismatch 検知の閾値

現行値: threshold **0.18** / 持続 **8s**（`core/oltw_follower.py`）

| 入力 | 閾値超えの最長連続秒数 |
|---|---|
| 別演奏（＝正解。誤検知してはいけない） | **5.4s** |

8s 持続を要求することで**別演奏の誤検知ゼロ**。これがこの機構の最重要ゲート。

**再校正手順（曲を変えたら必須）**: 別演奏を `eval_tracking` に流し、`raw_local_cost` が threshold を超える最長連続秒数を測る。その値 < `mismatch_seconds` を必ず確認する。

**解消不能な限界**（閾値緩和で破ろうとしないこと。破ると上記の誤検知ゼロが崩れる）:

1. 白色ノイズはコスト帯が matched と重なり検知できない
2. ずれ先が自己類似箇所だと局所コストが**本当に一致する**ため、検知もリカバリも原理的に不能

offset-60 実験の観測: probe 候補が反復テーマの 2 クラスタ間で振れ、四重ガードが正しく棄却した。検知フラグ側も「別の提示部で本当にマッチ」して解除される。

### リカバリ probe の四重ガード

`_probe_decisive_forward_match`（前方 10s 窓、1s ごと）:

| # | ガード | 値 |
|---|---|---|
| ① | cost margin | 0.08 |
| ② | discriminability ratio | 0.75 |
| ③ | **絶対 ceiling** | 0.08（matched 帯のみ） |
| ④ | **2 連続 probe の位置整合** | 候補が演奏進行 ~1.0 rate と整合 |

③ は過去の catchup 失敗（相対ガードのみだった）を受けて追加。④ は瞬時コストの裾が偶発的に ceiling を割っても 1s 後に整合位置で再発しない限り跳ばせない仕組みで、**違う楽章入力での誤テレポート 2 件をこれで根絶した実測がある**。

## 2. 表示確信度の LO と HI

現行値: **LO 0.05 → HI 0.22**（`core/result_handler.py`、融合コスト 5 フレーム平滑を 1→0 に線形写像）

校正に使ったコスト分布（幻想4、`raw_local_cost` の p50）:

| 入力 | cost |
|---|---|
| 同録音 | 0.014 |
| 別演奏 | 0.082 |
| 違う楽章（同一オケ） | 0.189 |
| 無関係なピアノ BGM | 0.300 |

**再校正手順**: eval CSV の `raw_local_cost` 分布を上表と同じ 4 条件で取り、matched 帯の上端と junk 帯の下端の間に LO/HI を置く。

### なぜ内部 confidence と分離したか

非負 chroma 同士の cosine には床があり（無関係な音でも cos 0.5–0.8）、内部 confidence は**無関係な入力でも 0.6–0.8 に張り付く**。「無関係なピアノ BGM で確信度 70%」という操作者の混乱の正体はこれで、特徴量の失敗ではない。

### 特徴量の判別能（実測）

- **無関係なピアノ BGM は特徴空間で明確に分離できている**（cost 0.300 vs matched 0.082 = 3.7 倍）。旧表示式が cost 0.30 → 70% に写像していただけ
- **本質的に重なるのは「同一オケの別の楽章」と「別演奏の正解楽章」**（junk p10 0.095 vs matched p90 0.159）。この重なりは特徴パラメータでは解消できない（→ [experiments.md](experiments.md#特徴量パラメータの-ab-テスト-onset-重みと-cens_win)）
- 白色ノイズ的な広帯域音は全ピッチクラスを含むため表示確信度も中間値（~50%）になる（既知の限界）

## 3. 慣性・DP まわりの実測

### 低 conf 自動 inertia entry を削除した根拠

オーケストラの pp passage は DP が正しい位置を低マージンで追えている状態が多い。慣性で上書きすると**別演奏のカバレッジが 100% → 34% に落ちる** regression を実測したため、低 conf 単独での慣性入りは完全削除した。

→ 再導入しないこと。詳細は [experiments.md](experiments.md#低-conf-自動-inertia-入り)

### 表示スルー（`display_slew_factor`）

別演奏の前進 stddev **0.66 → 0.42**、カバレッジ・conf に回帰なし。

### `low_conf_advance_frames`（既定 0 = 無効）

幻想4 実測で有意差なし。機構は残してあるが無効で出荷している。

## 4. 合成 BPM の自動推定

```
estimated_bpm = total_beats * 60.0 / ref_duration_sec
```

実例: 幻想4（178 measures × 4 beats = 712 beats）/ 281.04s ≈ **152 BPM**。

楽譜指示の 120 BPM で固定合成すると、ベルリン・フィルのような速い演奏（281s）との **27% のテンポ差**が MrMsDTW のスキップ大量発生（**21% のステップで score 側のみ進む**）を招き、`WarpLookup.validate`（slope 4.0x 上限）で失敗する。

sanity range `[20, 400] BPM` 外なら ERROR 停止、参照 duration 5.0s 未満は推定不可エラー。

## 5. 末尾無音の自動トリム

検出条件: ピーク −45dB 以下が 1.5s 超（`_detect_tail_silence_sec()`）

実測: 幻想4 の Berlin 参照録音は**末尾 8.23s が無音**。

| | BPM 推定値 | 到達小節 |
|---|---|---|
| トリム前 | 152.0 | 全入力が **m=173/178 で頭打ち** |
| トリム後 | 156.6 | 同録音・別演奏 2 種すべて **178/178** |

トリムしないと 2 つの故障が同時に起きる:

1. BPM 推定の分母（ref_duration）が水増しされ合成テンポが遅くなる
2. MrMsDTW がスコアの最終小節群を無音尾部にマップする → 無音区間の CENS はどの演奏ともマッチしないので、**runtime はどの入力でも最後の数小節に到達できない**

## 6. 先頭雑音の自動トリム

動作点: `_HEAD_DETECT_SEARCH_SEC=2.5s` / `_HEAD_DETECT_CENS_WIN=11` / `_HEAD_DETECT_CONTRAST_MIN=0.15` / `_HEAD_DETECT_BACKOFF_SEC=0.2s`

**人工雑音での検証**（校正用の実雑音入り録音がないため、実録音の頭に人工雑音を付加して代替）:

| 付加した雑音 | 結果 |
|---|---|
| チューニング A 音 | 真の開始位置を超えて切り込まず（誤差 −0.5〜−1.2s の under-trim） |
| 広帯域ノイズ | 同上 |
| 「無音 + A 音 + ブレス」複合 | 同上 |
| クリーンな冒頭（雑音なし） | 誤トリムなし |

**一度も over-trim しなかった** = 安全側に倒れている。

**実データ**（幻想4 Berlin 録音）: 自動検出 **1.86s**（内訳はほぼ純粋な先頭無音 ~1.75s + 比較による微調整）。トリム有無で warp 検証・coverage 178/178・別演奏 eval のカバレッジ/確信度に**回帰なし**。

> 同録音 eval で stall が微増したのは「トリム後の参照 vs 未トリムの同ファイルをそのまま live 入力に使う」という検証手法特有のアーティファクト。本番の手動スタート + silence gate 下では発生しない。

**未校正の限界**: 実際に頭雑音が入ったリハ/ゲネプロ録音での `_HEAD_DETECT_DROP_FRAC` / `_HEAD_DETECT_BACKOFF_SEC` の最終校正はまだ行っていない。検出結果に違和感があれば `--start-offset` で明示上書きする。

## 7. 無音判定閾値の式

```
threshold = median + (median − p10) + margin_db      # margin_db 既定 2dB
```

margin は Issue #19 で 3dB → 2dB に緩和。

**なぜ下側分布幅の鏡映か**: gate は「音量 ≤ 閾値で freeze」なので閾値は暗騒音分布の**上側**に置く必要がある。低いパーセンタイルをそのまま使うと gate がほぼ発動せず、高いパーセンタイル（95% 等）は測定中の偶発音（咳・会話）で吊り上がる。下側分布幅の鏡映はその両方を回避する。

**スプレッド床（旧 `MIN_SPREAD_DB=6dB`）を撤廃した根拠**（Issue #19）: 暗騒音が安定した環境では床が支配して閾値が median+9dB になり、弱音の入力が閾値を越えられず **gate が永遠に開かず追随が始まらない**。

実測: threshold **−12.9 dBFS** / median **−21.9 dBFS**。

手動スタート + one-shot gate 統治（Issue #13）導入後は誤スタート抑止の主役が手動スタートに移り、gate 誤開放が影響するのは開始押下〜最初の持続音の短い窓だけ（開放には `gate_activation_sec` の連続音も必要）。したがって「開かない」失敗の方が致命的、という判断。

## 8. eval_tracking のベースライン

```bash
python tasks/eval_tracking.py --built-dir <dir> --score <mxl> --input-wav <wav> [--oltw-kwargs '{...}']
```

| 入力 | カバレッジ | conf |
|---|---|---|
| 同録音 | 100% | 0.93+（最終確認では 0.95+） |
| 別演奏 | 96–100%（97%+ を目安） | — |

**新曲では最初に同録音 / 別演奏の 2 種を流して曲固有のベースラインを取ってから比較する。** 上の数値をそのまま新曲の合格基準に使わないこと。
